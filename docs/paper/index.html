Ranked Refresh Queue for Search Visibility Loss: A Machine Learning Decision-Support Tool

Capstone research paper · FlyRank ML Internship, July 2026 Cohort
Growth / Recovery / Momentum lane · Published 2026-09-30
Abstract

Question: Of the thousands of pages an editor must review each cycle, which ones deserve the first look?

Data: 9,841,378 daily Search Console observations from March 2026 across 38 pseudonymized clients, rolled up to 151,981 page-level feature rows and labeled down to 77,400 pages with 100+ first-half impressions.

Method: Five features computed over the first half of March (log impressions, CTR, average position, active days, log age), logistic regression with no scaler, validated with GroupKFold(5) grouped by client so no client leaks across the split. Label: did the page lose impressions in the second half of March — a within-month proxy, not a forecast.

Result: Grouped AUC 0.5902 vs 0.5000 random; P@50 0.4800 vs 0.4080 random. The model clears random ranking modestly but does not separate from the hand-written Week-4 rule at P@50 0.4360. One finding holds: pages below median CTR decline at 0.5072 vs 0.3804 above it. The "old pages decay more" heuristic runs backwards — the oldest quartile declines least, at 0.3707.

What it's for: A reading order for a human reviewer, not an automation. Nothing in the shipped queue is a refresh decision; every action is a look.

1. Introduction / Problem statement

A content team owns thousands of pages per client. One editor gets through a handful per cycle. The team already had Search Console data — impressions, clicks, average position, active days — sitting in spreadsheets.

What they did not have was an order. Every queue I had seen was either a spreadsheet sorted by impressions descending, which puts the biggest pages on top whether or not anything is wrong with them, or an editorial judgment call that nobody could write down and nobody could check later.

So the question was narrow: of the pages this editor has to look at anyway, which ones deserve the look first?

This is a decision-support problem, not an automation problem. The editor still reads the page. The model's job is to reduce the time before the first meaningful look.

What one row means

In the fact table, one row = one Search Console observation for one page in one client's account on one calendar day. When I build features to rank pages, I roll those daily rows up to one row per page at the decision date — the editor gets a ranked queue of pages, not of days.

Label

is_visibility_loss = 1 when a page's second-half March impressions are below its first-half impressions, computed only for pages with ≥ 100 first-half impressions. This is an honest within-month proxy for "this page is losing search visibility" — it is measured from the outcome window, which is never a feature. The label is a proxy, not a forecast of future decline, and I say so everywhere it appears.

Filtering and exclusion

  • Volume floor: pages with fewer than 100 first-half impressions are excluded from the label. This leaves 77,400 labeled pages out of 151,981 rows in the feature frame — 50.9% of the frame. This is a high-traffic queue. I did not solve the problem for thin pages, and I am not going to pretend the demo covers them.
  • GSC availability: only rows where gsc_data_available IS TRUE are used. 3,611,061 of 9,841,378 month rows survive this filter. GA4 rows carry a three-valued availability flag (TRUE / FALSE / NULL) with zero-filled early history — mixing a second, messier measurement system into this contract buys noise, not signal, so GA4 columns are excluded.
  • Product flags: health_score, priority_score, and similar product-internal flags are deliberately absent from this dataset. I must not rebuild them as features.
  • IDs: client_hash_id and content_hash_id are pseudonyms. They are used for grouping and for the client-holdout split only — never as features.

Coverage caveat

Per-client GSC history does not start together. Of 104 clients in the dimension table, 37 have no gsc_data_start, and only 52 cover all of March 2026. Equal calendar windows do not mean equal history depth. The 38 clients contributing labeled pages are a subset, with a median of 485 labeled rows per client and a maximum of 17,610.

3. Methodology

Features

Five features, each knowable at the decision moment. No scaler. No feature engineering beyond the definitions below.

FeatureDefinition (feature window only)Available when?
f_log_impressionsln(1 + first-half GSC impressions)Every input row was delivered by the daily sync on or before 2026-03-15
f_ctrfirst-half clicks ÷ first-half impressionsClicks arrive in the same daily sync as impressions, all dated ≤ 2026-03-15
f_avg_positionmean GSC position over impression-days in the first halfAveraged only on dates ≤ 2026-03-15
f_active_daysnumber of distinct first-half days with ≥ 1 impressionThe 15-day window is already complete at the decision
f_log_age_daysln(1 + days between page creation and 2026-03-15)Page creation date is static metadata known before any March data

Model

Logistic regression: LogisticRegression(max_iter=500, C=1.0), no scaler, fitted on all 77,400 labeled rows. I chose a readable linear model before reaching for anything more flexible — the queue is a decision-support tool for one person with a short list, and interpretability matters more than marginal AUC gains that I could not validate honestly anyway.

Important: The full-frame fit ranks rows the model has already seen, so the score itself is not an out-of-fold number. I quote no in-sample AUC for it anywhere. The only validated numbers are the out-of-fold ones from the grouped split below.

Validation design

GroupKFold(5) grouped by client_hash_id. No client sits in both train and test. This mattered more than I expected: the same model on a random row split scores AUC 0.6262, and grouping gives 0.036 of that back, which turns out to be client memorization rather than generalization. One grouped fold lands at 0.4666, below chance. I quote the grouped number everywhere and I would push back on anyone quoting the other one.

DesignAUCNotes
Grouped (client-holdout)0.5902Folds 0.4666 to 0.6547, SD 0.0646 — the number I quote

Leakage checks

I ran a deliberate leak test. I added one feature that should never be allowed — ln(1 + second-half impressions), literally the outcome window's defining quantity — and watched a quick 3-fold score jump to 1.0. Then I deleted it and the honest number (0.6262) came back. The bad run stays in the leakage section; the clean run is the result. A checklist can say "no leakage" even when the check is weak. A test that reacts to a known bad field gives more evidence that the boundary is working.

Baseline

The Week-4 rule: a hand-written heuristic built before any model, using the same grouped folds. It fits nothing — it is a fixed ordering rule. Its P@50 on the grouped folds is 0.4360, with per-fold values swinging from 0.20 to 0.58.

The model clears random ranking on both AUC and P@50. It does not beat the Week-4 rule — the gap of 0.0440 on P@50 sits inside the rule's own fold-to-fold spread of 0.38. I am calling them unseparated, not claiming a win. A 0.0440 difference on a metric whose baseline moves 0.38 between folds is not a result.

The chart

What held: the CTR split

Split the labeled set at the median CTR of 0.00135. Below the median, decline runs at 0.5072. Above it, 0.3804. That is a 0.1268 gap on 77,400 rows, and low_ctr_more_decline is the only one of the five reason codes whose assigned group finishes above the base rate.

What did not: the age story

I started from a reasonable-sounding assumption that old pages decay more. The oldest quartile declines at 0.3707, which is the lowest of the four quartiles, below the newest at 0.4074 and below the base rate of 0.4438. The pattern is not monotone anywhere — it peaks in the second quartile at 0.5458. I killed the stale_high_traffic reason code and assigned it to zero pages, because a heuristic that runs backwards in the data is worse than no heuristic at all.

Feature importance

On permutation importance, f_ctr is 0.0602 and f_active_days is 0.0596, with standard deviations of 0.0026 and 0.0015. They overlap within one SD, so they are tied, and ranking one above the other would be overclaiming. f_avg_position at 0.0010 is indistinguishable from zero. The claim I can defend is that low CTR is the only reason code with a measured lift — not that it is the strongest lever in the model.

5. Limitations & honest framing

  • The label is a within-March proxy, not a true future-window label. is_visibility_loss compares the second half of March to the first half — it is measured, not predicted, and it says nothing yet about whether today's features predict next month's decline. The capstone label must be built as prior window → future window and validated with time-aware splits.
  • One month, one decision date. March 2026 only. Seasonal effects, platform changes, and client-specific events in that month are baked in and unmeasured.
  • High-traffic pages only. The 100-impression floor excludes thin pages. 49.1% of the feature frame does not earn a label, and I make no claim about them.
  • 38 clients. The labeled set covers 38 of 104 clients in the dimension table, unevenly sized. The grouped split protects against client memorization but does not make the sample representative of all clients.
  • In-sample scores. The queue scores are full-frame fit probabilities. They are a sorting device whose ranking quality is known to be modest (grouped AUC 0.5902). I quote no in-sample AUC for them.
  • Model does not beat the rule. The 0.0440 P@50 gap is inside the rule's fold noise. The honest headline is that the model and the rule are unseparated.
  • Close to a single-signal queue. After the priority contest, only low_ctr_more_decline files a group above the base rate. The reason column stays — each code names a real measured pattern — but it should not be read as five independent findings.
  • Impressions are the only signal. The label is defined on impressions. A page that loses impressions but holds clicks, or vice versa, is not captured by this proxy.

I use careful words throughout: observed, measured, directional, decision-support. The model is a reading order. A person still reads the page.

6. Ranked recommendations

The audience for this section is one person: an editor opening a queue on the morning of a decision date and asking "which pages do I look at first, and why?" This is decision-support. It is not an automation, and nowhere in this queue does an action become a refresh decision.

  1. Look at low-CTR pages first. Pages below the median CTR of 0.00135 decline at 0.5072 vs 0.3804 above it — the only measured lift any pattern shows over the 0.4438 base rate. The action is a look at intent match and whether the page still answers the query it targets. Do not automate a refresh based on this.
  2. Do not trust the "old page" heuristic. The oldest quartile declines least (0.3707). Age is not a measured decline signal in this slice. Staleness is a real editorial reason to look at a page, but it is not what this label measures, and putting it in the reason column would borrow credibility the number does not have.
  3. Treat the queue as a sort, not a score. The full-frame fit probabilities are in-sample. The only validated number is grouped AUC 0.5902, which is modest. The editor gets an order; the probability column is context, not a confidence interval.
  4. Every action is a look. No row in this queue carries a refresh action. The best measured lift any single pattern shows over the base rate is +0.0634. That does not justify telling an editor to change a page. Deciding to refresh stays a human decision made outside this artifact.
  5. Read the reason codes as descriptions, not diagnoses. All five say "these pages share a measured feature pattern." None says why the pattern exists, and none is a prediction. The five codes:
    • low_ctr_more_decline — few people who see the page click it. Decline 0.5072 vs 0.3804. Action: ctr_review (a look).
    • high_volume_tilt — a high-traffic page. Tilt +0.0191, small. Action: monitor.
    • poor_position_drift — average position in the worse half. Action: position_check (is this a stable snapshot or a trend? — a question for a human).
    • low_activity_concentration — indexed on ≤ 10 of 15 days. These pages declined least (0.1251). Action: monitor_low_priority. This code exists to retire the naive story and make the negative result visible in the queue itself.
    • no_measured_pattern — nothing above fired. Explicitly low priority.
  6. Watch the middle of the queue. The ordering does most of its work in the first two deciles and then coasts. Deciles 5 through 9 all land between 0.4952 and 0.5532 decline rate. If the editor only has time for 50 pages, the top of the queue is where the signal is; the middle is close to the base rate.

Seeds and tie rule

The grouped folds use a fixed random seed for reproducibility. The tie rule for the ranked queue is: when two rows have the same score, rows are ordered by descending impressions, then by descending clicks — a fixed rule that makes the order repeat when another person runs the code.

The fair comparison contract

Model and baseline: same eligible rows (77,400 labeled pages), same client folds (GroupKFold 5), same metrics (AUC, P@50), same review depth K=50, same tie rule, base rate shown next to both. The baseline fits nothing — it is a fixed ordering rule.
